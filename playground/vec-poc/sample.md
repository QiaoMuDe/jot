# 本地笔记应用架构与 AI 助手设计文档

本文档用于向量召回 POC 的测试素材，描述一个本地优先的笔记应用的架构设计、AI 助手功能、卡片召回与向量检索的技术方案。所有数据保存在本地，隐私优先，AI 能力由 Ollama 本地模型与互联网大模型协同提供。

## 总体架构

本应用采用"本地优先（Local-First）"的架构原则：笔记数据以 Markdown 文件与 SQLite 数据库双轨存储，全部落在用户本机，不依赖云端同步。应用核心分为三层：存储层、检索层与应用层。

存储层使用 SQLite 作为唯一的本地数据库，保存文档元数据、切块后的文本以及对应的 embedding 向量。SQLite 轻量、免部署、单文件即可携带，非常适合桌面级应用。为了保证读写性能，数据库开启 WAL 模式（Write-Ahead Logging），并设置 busy_timeout 避免多线程访问时的锁冲突。

检索层是本次 POC 的重点。我们将文档切块后调用 Ollama 本地 embedding 模型（如 bge-m3）生成向量，向量以 float32 小端序 BLOB 形式存放在 SQLite 的 blob 列中。检索时优先使用 sqlite-vec 扩展提供的 vec_distance_cosine 函数在 SQL 内部完成最近邻搜索，若扩展不可用则回退到纯 Go 暴力扫描。

应用层提供三个主要功能：笔记编辑、卡片浏览、AI 问答。AI 问答通过 RAG（检索增强生成）流程实现：先向量召回相关片段，再把片段与问题一起交给大模型生成回答。

## 数据模型设计

数据库主要包含两张表：documents 与 chunks。documents 表保存文档主记录，字段包括 ID、文件名、源路径、全文内容与创建时间。chunks 表保存切块记录，字段包括 ID、所属文档 ID、块序号、块文本、embedding 向量 BLOB、向量维度、embedding 模型名与创建时间。

将文档与块分离是为了支持增量更新：当某个文档被重新导入时，只需删除该文档对应的块再重建，而不影响其他文档的索引。向量按模型名区分，这样即使更换 embedding 模型，也能通过模型名过滤旧向量，避免混用不同维度的向量造成检索错误。

## 卡片与卡片召回

笔记应用以"卡片"为基本交互单元。一张卡片对应一个语义完整的段落或章节，用户可以在卡片之间自由跳转、建立双链引用。卡片化的好处是信息粒度小，便于阅读与重组；而在检索侧，卡片天然对应一个检索单元（chunk），语义更聚焦。

卡片召回流程如下：用户输入查询后，应用先用与索引相同的 embedding 模型把问题编码为查询向量，然后在 chunks 表中按余弦距离排序，取距离最小的前 K 个块作为召回结果。召回结果按距离升序展示，同时回填所属文档名，方便用户定位原始笔记。

为了提升召回质量，我们会对文档做预处理：去除无关的 Markdown 标记、按标题与空行切块、过滤过短的空块。切块大小默认控制在 500 字以内，避免单块语义混杂；长段落会做硬切，保证每块长度可控，从而让 embedding 更精准。

## RAG 召回与问答流程

AI 助手的问答走完整的 RAG 流程，分为四个步骤。

第一步，知识入库：将用户导入的 Markdown 笔记读取出来，用切块器切分为若干块，批量调用 Ollama 的 embedding 接口生成向量，写入 chunks 表。

第二步，问题向量化：用户提问时，用同一 embedding 模型将问题编码成查询向量。

第三步，向量召回：执行最近邻搜索，取出 topK 个最相关的块。这里注意，检索必须使用与索引相同的 embedding 模型，否则向量空间不一致，召回结果会完全失效。

第四步，生成回答：把召回片段组装成 system 提示词，说明"以下是知识库中与问题相关的片段，请优先基于这些片段回答；若片段不足以回答，请如实说明"，再把用户问题作为 user 消息，调用 OpenAI 兼容接口的对话模型生成回答。这样既利用了本地知识库的私密信息，又借助了互联网大模型的推理能力。

## 分词与本地处理

对于中文文本，单纯按空白切分无法得到有意义的词元。应用在索引阶段使用 gse 分词器对中文内容做分词统计，辅助标题抽取与关键词提取，让切块边界更贴合语义单元。分词结果还可以用于生成卡片摘要，让卡片在列表视图中更容易被扫读。

gse 是一款纯 Go 实现的轻量分词库，支持自定义词典与词性标注，适合在本地嵌入式场景中使用，不引入额外的运行时依赖。分词与向量化都在本机完成，笔记内容不会上传到任何第三方服务器。

## OpenAI 兼容接口与模型选择

对话与向量化走两条独立的链路。向量化固定使用 Ollama 本地模型，保证数据不出本机；对话则通过 OpenAI 兼容接口调用，既支持本地模型（如 Ollama 提供的 /v1 兼容端点），也支持互联网大模型服务，二者只需切换 baseURL 与模型名即可。

OpenAI 兼容接口的标准做法是：POST /v1/chat/completions，请求体包含 model、messages 数组（role 取 system 或 user），响应中取 choices[0].message.content 作为回答文本。我们的 llm 客户端封装了这一流程，并支持自定义 baseURL，因此可以无缝对接 Ollama、DeepSeek、通义千问等任意兼容服务。

## 检索性能与回退策略

sqlite-vec 扩展在 SQL 层执行向量距离计算，数据无需读出数据库，性能显著优于纯 Go 暴力扫描。但扩展依赖特定版本的 SQLite 编译产物，在部分平台可能无法加载。为此应用在启动时执行 SELECT vec_version() 做探针检测：探针成功则启用 sqlite-vec 实现，失败则自动回退到纯 Go 暴力检索实现。

暴力检索实现的逻辑是：一次性加载全部块的向量，逐条解码 BLOB 并计算余弦相似度（距离 = 1 - 相似度），排序后取 topK。虽然复杂度是 O(N)，但对于个人笔记这种万级规模的数据量，性能完全可接受，且不依赖任何外部扩展，稳定性最高。

## 命令行工具与验证

为验证上述技术路线，我们提供 vec-poc 命令行工具，支持 add（导入文档）、index（重建索引）、ask（RAG 问答）、list（列出文档）、status（查看状态）五个子命令，并支持无参数启动进入交互式 REPL。工具启动时会打印 sqlite-vec 探针结果与检索实现类型，方便观察回退行为。

验证场景建议：先用 add 导入本文档，再用 ask 提出"卡片召回流程是怎样的"或"数据库用了什么存储引擎"等问题，观察召回片段的距离排序与回答质量。若召回距离普遍较大，说明查询与文档语义偏离，可尝试换用更强的 embedding 模型或调整切块大小。
